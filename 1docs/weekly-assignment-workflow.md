# 주간 과제 운영 흐름과 저장소별 담당 위치

이 문서는 교수용 운영 설명서다. 에이전트 행동 규칙의 원천은 [AGENTS.md](../AGENTS.md), 실제 채점에 사용하는 주차별 마감 데이터의 원천은 [deadline.csv](../5input/deadline.csv)다.

**현재 상태: 운영 일정 정리 중.** 아래에는 사용자가 설명한 운영 의도와 현재 구현의 차이를 구분해 기록했다. 이 문서를 작성하면서 마감 데이터, 채점 코드, 학생 공개 자료나 구글 시트를 변경하지 않았다. 일정 적용 시작 주차와 미확정 사항을 정한 뒤 관련 원천을 일치시켜야 한다.

## 1. 주차는 평가하는 랩의 번호를 기준으로 식별한다

수업을 진행하는 주차와 상호평가 대상 랩의 주차는 다를 수 있다.

| 구분 | 의미 | 3주차 수업 후 예시 |
|---|---|---|
| 수업 주차 | 현재 수업을 진행하는 주차 | 3주차 |
| 이메일 과제 번호 | 해당 수업 주차의 마이크로 과제 | `0.3` |
| 랩 과제 주차 | 학생이 새로 제출하는 실습 과제 | 랩3 |
| 상호평가 대상 주차 | 동료가 제출한 과제 중 이번에 평가하는 랩 | 랩2 |

따라서 3주차에 랩2를 상호평가하더라도 배정표와 평가 응답의 대상은 **랩2**다. 평가를 수행한 주차를 이유로 랩2 배정을 랩3 배정으로 바꾸지 않는다.

사용자가 요청한 **7주차 배정은 랩7 제출물에 대한 신규 배정**이다. 기존 랩6 배정을 랩7로 바꾸거나 다시 추첨하는 요청이 아니다.

## 2. 사용자가 설명한 주간 운영 흐름

모든 시각은 한국 표준시(KST) 기준이다.

| 시점 | 학생 또는 시스템의 작업 | 담당 위치 | 확정 상태 |
|---|---|---|---|
| 3주차 수업 후 | 이메일 `0.3` 및 랩3 과제 수행 | 과제 안내: `stu2603` | 사용자 설명 |
| 그 주 목요일 23:59까지 | 이메일 `0.3` 제출 | 수집·채점: `eval-stu` | 사용자 설명, 기존 이메일 정책과 일치 |
| 그 주 금요일 23:59까지 | 랩3 제출 | 접수·제출본 확정: `eval-stu` | 사용자 설명, 기존 문서·데이터와 불일치 |
| 3주차 수업 후 해당 평가 기간 | 기존 배정에 따라 랩2 상호평가 응답 제출 | 배정·응답 집계: `eval-stu` | 평가 대상은 랩2, 정확한 마감은 확인 필요 |
| 토요일 00:00 | 랩2 상호평가 루브릭 공개 | `stu2603` | 담당 저장소·요일·시각은 사용자 설명, 어느 주 토요일인지는 확인 필요 |

금요일 23:59 마감 직후가 토요일 00:00이다. 프로그램에서 경계 시각을 표현할 때 두 시각의 포함·제외 방식도 일치시켜야 한다.

### 일정 확정에 필요한 확인

1. **랩2 루브릭 공개 토요일은 어느 주인가?** 3주차 중에 랩2 평가를 제출해야 한다면, 그 평가에 필요한 루브릭은 제출 전에 열람할 수 있어야 한다. 이전 주 토요일 공개인지, 같은 주 토요일 공개 후 평가를 시작하는 것인지 확인해야 한다.
2. **상호평가 응답의 정확한 마감은 언제인가?** 사용자 설명에는 랩2 상호평가 제출 의무가 있지만, 그 마감 시각이 금요일 23:59라고 별도로 확정되지는 않았다. 기존 학생 안내는 목요일 23:59다.
3. **금요일 랩 마감을 어느 주차부터 적용하는가?** 이미 제출·채점한 과제의 정시·지각 판정을 소급해서 바꿀지 여부는 별도로 정한다.

위 항목이 확정되기 전에는 공개 순서를 추정해 자동 배포를 설정하거나, 새로운 마감으로 학생 점수를 다시 계산하지 않는다.

## 3. 현재 원천 간 차이와 반영 위치

| 항목 | 현재 문서·구현 | 사용자가 설명한 운영 | 반영할 원천 |
|---|---|---|---|
| 이메일 마감 | 목요일 23:59, 별도 유예 정책 존재 | 목요일 23:59 | [이메일 채점 정책](score-email.md), `deadline.csv` |
| 랩 마감 | `stu2603` 안내는 일요일 23:59, `eval-stu` 정책·코드는 다음 월요일 분반별 수업 시작 전 | 금요일 23:59 | `stu2603/AGENTS.md` 및 공통 학생 안내, `eval-stu/AGENTS.md`, [랩 채점 정책](score-lab.md), `deadline.csv`, 마감 해석 코드 |
| 상호평가 마감 | `stu2603` 공통 학생 안내는 목요일 23:59 | 이전 주차 랩을 평가, 정확한 마감 확인 필요 | `stu2603` 학생 안내 및 평가 일정 데이터 |
| 루브릭 공개 | 원본 파일 존재와 학생 공개 여부를 구분해 확인해야 함 | 토요일 00:00, `stu2603`에서 공개 | `stu2603`의 공개 설정·자동화와 실제 학생 열람 링크 |
| 기존 배정 보존 | 일부 기존 도구는 탭 전체 삭제 후 재작성 | 랩6 보존, 랩7 별도 배정 | `eval-stu`의 배정·제출본 동기화 도구 |

현재 [랩 채점 정책](score-lab.md)의 다음 수업 전 마감은 새 운영 의도와 일치하지 않는다. 원천별 수정을 마치기 전에는 새로운 금요일 마감이 코드에 적용됐다고 간주하지 않는다.

`stu2603`의 기존 운영 지침상 K트랙(4반)은 상호평가를 기본 실시하지 않는다. 웹 1·2반의 배정을 4반에 자동 확대하지 않으며, 4반에 대한 별도 실시 요청이 있으면 그 범위에 맞춰 처리한다.

## 4. 작업별 담당 저장소

| 요청 또는 산출물 | 담당 저장소 | 이 저장소에서 찾을 위치 |
|---|---|---|
| 강의안·핸드아웃·랩 과제 내용 | `stu2603` | `5input/py`, `5input/web`로 읽기 참조 |
| 루브릭 작성·수정·학생 공개·공개 예약 | `stu2603` | 주차별 `peer-eval-rubric.md`는 읽기 참조 |
| 학생 명부 추가·수정 | `stu2603` | `5input/students`는 읽기 참조 |
| 이메일 수집·채점·피드백 답장 | `eval-stu` | `bin/grade.sh`, `1docs/score-email.md` |
| 랩 제출본 수집·중복 제거·상호평가 배정 | `eval-stu` | `bin/sync_lab_submissions.py`, `bin/assign_peer_review.py` |
| 상호평가 응답 집계·랩 채점·성적부 반영 | `eval-stu` | `bin/check_evaluations.py`, `modules/`, `1docs/score-lab.md` |
| 주간 일정 전체를 검토 | 이 문서에서 양쪽 저장소의 원천을 함께 확인 | 일정 확정 후 각 담당 저장소의 원천에 반영 |

위 도구 경로는 담당 기능을 찾기 위한 안내다. 현재 채점·동기화 도구에서 발견된 문제를 수정하지 않은 상태이므로, 명령을 실행하면 위 운영 흐름이 모두 구현된다고 보장하지 않는다.

## 5. 배정 보존과 공개 확인

기존 배정은 대상 랩 주차에 연결된 기록으로 보존한다. 랩6과 랩7의 배정표·제출본·평가 응답을 각각 구분하고, 새 주차 작업 때문에 이전 주차 자료를 지우지 않는다.

현재 요청에서 랩6 루브릭은 공개되지 않았다는 사용자 설명이 있다. 랩6 배정을 유지하며, 루브릭 미공개로 평가할 수 없었던 상황을 학생의 미참여로 단정해 감점하지 않는다. 공개 확인과 평가 기회 확보를 먼저 다룬다.

랩7은 랩7 제출본을 확인해 별도로 배정한다. 랩7 제출이 없으면 랩6 제출물을 대신 쓰지 않는다. 배정 실행 여부와 별개로 루브릭 파일의 존재, 학생 공개, 평가 응답 접수, 점수 확정 상태를 각각 확인한다.

## 6. 저장소 통합 결정과 전환 전 작업 위치

**사용자 결정: 두 저장소를 하나로 통합한다.** 기존 비공개 `stu2603`에 채점 기능을 `eval/`로 편입하는 [저장소 통합 계획](repository-unification-plan.md)을 작성했다. [추적 이슈는 stu2603 #244](https://github.com/wonhyukc/stu2603/issues/244)다.

통합 계획은 Git 이력·기존 배정 보존, 공통 일정, CI·GitHub Actions, 공개 자동화, 검증과 복구 절차를 포함한다. 이전이 완료되면 하나의 저장소 안에서 강의 준비와 평가를 수행한다. 학생용 배포 저장소는 유지한다.

아직 실제 이전은 실행하지 않았다. 따라서 위 작업별 담당 저장소 표는 **전환 전 현재 구조**를 설명한다. 통합 완료 시 담당 위치를 같은 저장소 내부 경로로 갱신한다.
